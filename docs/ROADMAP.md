# ROADMAP: Notion CMS 기반 유니티 개발 일지 / 포트폴리오 사이트

> 기준 문서: [PRD.md](./PRD.md)
> 목표: Notion에 글을 쓰면 코드 수정 없이 사이트에 반영되는 포트폴리오 사이트를 배포한다.
> MVP 총 예상 시간: 약 **50~60분** (PRD의 30분 목표는 숙련 시 기준이며, 아래는 확인·검증 시간을 포함한 현실적 추정)

## 진행 현황

| 단계 | 이름 | 예상 시간 | 상태 |
|---|---|---|---|
| 1 | 프로젝트 초기 설정 | 10~15분 | 🟡 진행 중 (`web/` 스캐폴딩 존재) |
| 2 | 공통 모듈/컴포넌트 개발 | 15분 | ⬜ 대기 |
| 3 | 핵심 기능 개발 | 20~25분 | ⬜ 대기 |
| 4 | 추가 기능 개발 | 별도 일정 (MVP 이후) | ⬜ 대기 |
| 5 | 최적화 및 배포 | 10~15분 | ⬜ 대기 |

> 의존 관계: 1 → 2 → 3 → 5 순서로 진행하고, 4단계는 MVP 배포(5단계) 이후 반복 개선으로 진행한다.
> PRD 기준 "첫 배포 URL"을 빨리 얻는 것이 성공 기준이므로 4단계는 배포 뒤로 둔다.

---

## 1단계: 프로젝트 초기 설정 (골격 구축)

**예상 소요 시간:** 10~15분

### 작업
- [ ] Notion Integration 생성 후 콘텐츠 데이터베이스에 Connections로 연결
- [ ] Notion DB 속성 구성 (Title, Slug, Type, Status, Published At, Summary, Cover, Genre, Engine Version, Tags, Play URL, Repo URL)
- [ ] 샘플 글 3개 입력 (Project 2, Devlog 1 이상, `Draft` 1개 포함해 필터 검증용)
- [ ] 공식 문서로 `@notionhq/client` 버전과 DB 조회 API(database vs data source) 확정 후 버전 고정
- [ ] Next.js(App Router) + TypeScript + Tailwind CSS 프로젝트 정리 (`web/`)
- [ ] 패키지 설치: `@notionhq/client`, `notion-to-md`, `react-markdown`
- [ ] `.env.local` 작성 (`NOTION_TOKEN`, `NOTION_DATABASE_ID`), `.gitignore`에 포함 확인, `NEXT_PUBLIC_` 접두사 미사용
- [ ] 디렉터리 골격 생성: `src/app`, `src/components`, `src/lib`
- [ ] 스타터 데모 코드와 기본 에셋 제거

### 왜 이 순서인가
- 모든 후속 작업이 Notion 토큰, DB ID, 확정된 API 방식에 의존한다. 여기서 API 방식을 틀리게 잡으면 `lib/notion.ts`부터 전부 다시 써야 한다(PRD 리스크 "API 버전 변경").
- 샘플 데이터가 있어야 이후 단계마다 실제 데이터로 바로 검증할 수 있다.

### 완료 기준
- [ ] `npm run dev`로 기본 페이지가 열린다.
- [ ] `npm run build`와 `npm run lint`가 오류 없이 끝난다.
- [ ] 토큰과 DB ID가 `.env.local`에만 있고 git 추적 대상이 아니다.
- [ ] 사용할 `@notionhq/client` 버전과 조회 방식이 이 문서 또는 코드 주석에 기록되어 있다.

## 2단계: 공통 모듈/컴포넌트 개발

**예상 소요 시간:** 약 15분

### 작업
**데이터 계층 (`src/lib`)**
- [ ] `types.ts`: `Post` 도메인 타입 정의
- [ ] `notion.ts`: Notion 클라이언트 초기화 (서버 전용)
- [ ] 속성 → `Post` 매핑 함수 (빈 값 기본 처리: `genre`, `tags`는 빈 배열)
- [ ] `getPosts(type?)`: `Status = Published` 필터 + `Published At` 내림차순 조회
- [ ] Slug 검증: 비어 있거나 중복이면 건너뛰고 빌드 로그에 경고
- [ ] `getPostBySlug(type, slug)`: 단건 조회
- [ ] `getPostBody(id)`: 블록 → Markdown 변환 (`notion-to-md`)
- [ ] 요청 직렬화 / 목록 조회 결과 재사용 (레이트 리밋 대응)

**공통 UI (`src/components`)**
- [ ] `Header` (로고, Projects / Devlog 내비게이션)
- [ ] `Footer` (GitHub / Email 링크)
- [ ] `ProjectCard` (커버, 제목, 요약, 장르 칩)
- [ ] `DevlogItem` (날짜 + 제목 + 요약)
- [ ] `PostBody` (`react-markdown`으로 제목, 문단, 리스트, 이미지, 코드, 인용 렌더링)
- [ ] 빈 상태 문구 컴포넌트
- [ ] `app/layout.tsx`에 Header/Footer 적용, 반응형 기본 틀 (모바일 1열, 데스크톱 3열)

### 왜 이 순서인가
- 페이지(3단계)는 "데이터를 가져오고 → 공통 컴포넌트로 보여주는" 조립 작업이다. 재료가 먼저 있어야 페이지를 한 번에 끝낼 수 있다.
- 데이터 계층을 UI보다 먼저 검증하면, 이후 화면 문제가 생겼을 때 원인이 Notion 연동인지 UI인지 분리된다.
- `Post` 타입이 확정되어야 컴포넌트 props가 흔들리지 않는다.

### 완료 기준
- [ ] 임시 페이지나 콘솔에서 샘플 3개 중 `Published`만 최신순으로 출력된다. `Draft`는 나오지 않는다.
- [ ] Slug가 비었거나 중복인 행에 경고 로그가 남고 크래시하지 않는다.
- [ ] 본문 변환 결과가 Markdown 문자열로 확인된다.
- [ ] 공통 컴포넌트가 하드코딩 샘플 props로 모바일/데스크톱 모두 정상 렌더링된다.
- [ ] 클라이언트 번들에 Notion 토큰이 포함되지 않는다 (서버 컴포넌트에서만 호출).

## 3단계: 핵심 기능 개발

**예상 소요 시간:** 20~25분

### 작업
- [ ] `/` 홈: 소개 문구 + 최근 프로젝트 3개 + 최근 일지 5개 + "전체 보기" 링크
- [ ] `/projects` 목록: 카드 그리드, 빈 상태 처리
- [ ] `/projects/[slug]` 상세: 커버, 제목, 메타(Genre · Engine Version · Published At), Play/Repo 버튼(값이 있을 때만), 본문
- [ ] `/devlog` 목록: 날짜 + 제목 + 요약 리스트, 빈 상태 처리
- [ ] `/devlog/[slug]` 상세: 본문
- [ ] `not-found.tsx` 404 화면, 존재하지 않는 slug 요청 시 `notFound()` 호출
- [ ] `generateStaticParams`로 SSG 구성 + `revalidate = 300` (ISR)
- [ ] 페이지별 `generateMetadata` (`title`, `description`)

### 왜 이 순서인가
- 방문자에게 가치를 주는 기능(목록과 상세)은 2단계의 데이터 계층과 컴포넌트를 조립해야 만들 수 있다.
- 홈이 목록/상세로 이어지므로 홈 → 목록 → 상세 순으로 만들면 PRD의 "홈에서 두 번 이내 클릭" 기준을 구현하면서 바로 확인할 수 있다.
- ISR과 SEO 메타데이터는 라우트 구조가 확정된 뒤에 넣어야 중복 수정이 없다.

### 완료 기준
- [ ] 모든 라우트가 샘플 데이터로 렌더링된다.
- [ ] 홈에서 2번 이내 클릭으로 프로젝트 상세에 도달한다.
- [ ] `Draft` 글은 목록에도, URL 직접 접근에도 노출되지 않는다 (404).
- [ ] 본문의 제목, 문단, 리스트, 이미지, 코드, 인용이 모두 정상 표시된다.
- [ ] 각 페이지의 `<title>`과 description이 올바르다.
- [ ] `npm run build`가 오류 없이 끝나고 정적 페이지가 생성된다.

## 4단계: 추가 기능 개발 (MVP 이후)

**예상 소요 시간:** 기능별 30분~2시간, MVP 배포 후 필요에 따라 선택

### 작업 (우선순위 순)
- [ ] 이미지 URL 만료 대응: 빌드 시 이미지를 내려받아 정적 자산으로 저장 (또는 `next/image` 최적화 경로 점검)
- [ ] On-demand revalidation: Notion 버튼/웹훅 → `/api/revalidate` (시크릿 검증 포함)
- [ ] 다크 모드 (시스템 설정 연동)
- [ ] 확장 블록 지원: 토글, 콜아웃, 테이블 (직접 블록 렌더러로 교체 검토)
- [ ] 태그/장르/Unity 버전 필터 페이지
- [ ] RSS 피드
- [ ] WebGL 빌드 iframe 임베드 (게임 허브)
- [ ] 검색, 다국어, 댓글

### 왜 이 순서인가
- 추가 기능은 모두 "동작하는 MVP"를 전제로 한다. 코어가 불안정한 상태에서 얹으면 문제의 원인을 찾기 어렵다.
- MVP를 먼저 배포하면 실제 사용(Notion 작성 → 반영) 경험에서 어떤 기능이 정말 필요한지 근거가 생긴다.
- 이미지 만료는 실사용 시 가장 먼저 체감되는 문제라 최우선으로 둔다.

### 완료 기준
- 기능별로 PRD의 해당 항목을 충족하고, 기존 라우트가 깨지지 않으며 `npm run build`가 통과한다.
- 이미지 대응: 배포 1시간 이후에도 본문과 커버 이미지가 깨지지 않는다.
- 재검증: Notion에서 변경 후 5분을 기다리지 않고 수 초 내 사이트에 반영된다.

## 5단계: 최적화 및 배포

**예상 소요 시간:** 10~15분 (배포) + 점검 시간

### 작업
- [ ] 스타일 다듬기 (여백, 타이포그래피, 모바일 레이아웃 확인)
- [ ] 빈 값/긴 제목/이미지 없음 등 예외 상황 UI 확인
- [ ] `next/image` 사용 및 `next.config` 이미지 도메인 설정
- [ ] 기본 SEO 점검 (title, description, OG 기본값)
- [ ] GitHub 푸시 → Vercel 프로젝트 연결 (Root Directory를 `web`으로 지정)
- [ ] Vercel에 환경변수 `NOTION_TOKEN`, `NOTION_DATABASE_ID` 등록
- [ ] 배포 후 Lighthouse로 성능/접근성/SEO 확인

### 왜 이 순서인가
- 최적화는 동작하는 기능이 있어야 측정할 수 있다. 먼저 하면 바뀔 코드를 최적화하는 낭비가 된다.
- 배포는 환경변수와 빌드가 안정된 마지막에 해야 실패 원인이 단순하다. 로컬 `npm run build` 통과가 배포의 사전 조건이다.

### 완료 기준
- [ ] 배포 URL에서 Notion 데이터가 보인다.
- [ ] Notion에서 `Draft` → `Published`로 바꾸면 5분 이내(ISR 300초) 사이트에 반영된다.
- [ ] Notion에서 제목을 수정하면 revalidate 시간 이후 사이트에 반영된다.
- [ ] Lighthouse 모바일 기준 Performance / Accessibility / SEO 90 이상을 목표로 한다.
- [ ] 저장소와 클라이언트 번들에 토큰이 노출되지 않았음을 확인했다.

## 리스크 체크리스트 (PRD 7장 기준)

| 리스크 | 확인 시점 | 대응 |
|---|---|---|
| API 버전 변경 | 1단계 | 공식 문서로 조회 방식 확정, 버전 고정 |
| 토큰 노출 | 1~2단계, 5단계 | 서버에서만 호출, `NEXT_PUBLIC_` 미사용, 번들 확인 |
| API 레이트 리밋 | 2단계 | 요청 직렬화, 목록 결과 재사용 |
| 지원하지 않는 블록 | 3단계 | 기본 블록만 사용하도록 작성 가이드 유지, 4단계에서 확장 |
| 이미지 URL 만료 | 4단계 (최우선) | 빌드 시 이미지 저장 또는 짧은 재생성 주기 |
